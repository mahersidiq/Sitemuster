# Supervised no-phone identity (Milestone 03 design; implemented in Milestones 05 and 08)

Source rules: decisions #1, #3; spec 01 "Worker without phone"; spec 02 "No-phone"; spec 04
"Kiosk / foreman / manual"; spec 05 `worker_profiles.managed_identity`.

## Goals

- A worker with no smartphone, no SMS-capable phone, or who refuses tracking can still be enrolled
  and attend through kiosk, foreman or manual sources.
- Never invent a phone number, an email, an SMS consent or an auth account (CLAUDE.md banned
  patterns; database constraint `worker_profiles_managed_ck`).
- No duplicate identities: one person, one worker profile.

## Creating a managed identity (supervised)

1. An authorized staff member (MFA; roster role on the project) or a kiosk attendant opens
   "Add worker without phone".
2. They record: legal name, employer (subcontractor), trade, preferred language, and optionally an
   emergency contact. No phone/email fields are required; none are fabricated.
3. Orientation is acknowledged in person: the operator confirms the worker received the approved
   notice (printed or read aloud) in EN/ES. Stored as an `orientation_records` row with
   `operator_id` and the notice version, plus a `tracking_consents` row with method `SUPERVISED`
   only if location tracking is relevant (it is not for a no-phone worker; attendance is kiosk/foreman).
4. Server function creates `worker_profiles` with `managed_identity = true`, `auth_user_id = null`,
   audited with the operator as actor. Employer confirmation and project approval stay separate
   steps (decisions #4, #56).
5. A printed opaque badge (`SMP1.…`, no PII) is issued with custody notes; source
   `KIOSK_PRINTED_BADGE` is always flagged as weaker evidence.

## Duplicate prevention

- Before creating, the server searches the project's company roster for the same normalized legal
  name + employer and shows possible matches to the operator; creation of a probable duplicate
  needs an explicit "different person" confirmation with a reason (audited).

## Claiming the identity later (phone becomes available)

1. The worker signs in with SMS OTP on their own phone (new auth user, no profile yet).
2. Linking requires BOTH: the worker scans a single-use claim code generated by an authorized staff
   member for that managed profile (in person), AND GC staff or the employer confirms the match.
3. The server moves the auth link onto the managed profile (sets `auth_user_id`, clears
   `managed_identity`) in one audited transaction; attendance history stays attached; the printed
   badge may stay active or be revoked by staff.
4. A managed profile can never be claimed by self-assertion (name match alone), by QR alone, or by a
   foreman alone.

## Out of scope for V1

Biometrics, ID-document scanning, and automatic merging.
